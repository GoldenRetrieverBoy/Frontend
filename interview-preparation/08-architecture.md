## ARC-01. Инкапсуляция, полиморфизм, наследование и композиция — зачем?

**Ответ.** Инкапсуляция защищает инварианты и скрывает детали реализации; полиморфизм позволяет работать с разными реализациями через общий контракт; наследование связывает типы и поведение. Композиция собирает объект из сотрудничающих частей и часто уменьшает жёсткую связь с базовым классом. Агрегация описывает связь с частью, которая может существовать независимо; это модель владения, а не специальный оператор JS.

```ts
interface Notifier { send(message: string): Promise<void> }
class Checkout {
  constructor(private notifier: Notifier) {}
  async notify() { await this.notifier.send('Заказ оформлен'); }
}
```

Checkout зависит от контракта: можно передать email-реализацию или тестовую. TypeScript interface исчезает в JS. Абстрактный класс может иметь общую runtime-реализацию; interface описывает форму без общей реализации. Статический метод принадлежит классу, обычный — поведению экземпляров.

**Практика:** замени иерархию «заказ с email, заказ с SMS, заказ с обоими» композицией. **Ошибка:** называть любую функцию с private полем хорошей инкапсуляцией, если инварианты всё равно нарушаются извне.

## ARC-02. Как применять SOLID без лишних абстракций?

**Ответ.** SRP — согласованные причины изменения; OCP — расширение подходящей точки без переписывания устойчивой части; LSP — заменяемость с соблюдением контракта; ISP — узкие интерфейсы для потребителей; DIP — политика зависит от абстракций, а не деталей. Это критерии проектирования, а не требование создать класс для каждого действия.

**Пример.** Расчёт цены принимает функцию скидки. Новая стратегия меняет скидку, но не оркестрацию. Если реализация «скидки» внезапно отправляет платёж, контракт нарушен. DRY касается дублирования знания; две случайно похожие формы не обязательно надо объединять. KISS уменьшает ненужную сложность, YAGNI откладывает неподтверждённые возможности.

**Практика:** общая форма с 20 boolean props обслуживает три продукта. Назови признаки неудачной абстракции, предложи разделение и оцени миграцию. **Уточнение:** когда дублирование дешевле общей библиотеки? При разных направлениях изменений и неустойчивом общем контракте.

## ARC-03. Какие паттерны реально применяются на Frontend?

**Ответ.** Выбираю паттерн по проблеме и цене. Factory централизует создание; Builder — последовательную сборку сложного объекта; Singleton — единственный экземпляр в выбранной области, но усложняет изоляцию/SSR. Strategy заменяет алгоритм, Adapter согласует интерфейс, Facade упрощает подсистему, Decorator добавляет поведение, Observer уведомляет подписчиков, Composite работает с деревом единообразно.

```ts
type Discount = (price: number) => number;
const withoutDiscount: Discount = price => price;
const tenPercent: Discount = price => price * 0.9;
const quote = (price: number, discount: Discount) => discount(price);
console.log(quote(100, tenPercent)); // 90
```

Это Strategy без классов. Учебная арифметика не задаёт production-правила округления денег. Observer требует unsubscribe; Singleton со сессией на сервере может смешать пользователей. Builder не нужен объекту из двух очевидных полей.

**Практика:** для двух поставщиков с разными DTO предложи Adapter к доменной модели, затем Facade для сценария поиска. Объясни, почему это две разные роли.

## ARC-04. Что разобрать «за пределами каталога паттернов»?

**Ответ.** Матрица не задаёт закрытый список. Берём state machine для явных переходов, circuit breaker для временного ограничения обращений к отказывающей зависимости, bulkhead для изоляции ресурсов и stale-while-revalidate для сочетания скорости/актуальности. Нужно объяснить конкретный контекст применения, а не заявлять, что эти названия отсутствуют на каком-то сайте.

**Пример state machine.** `idle → submitting → success | error`; повторная отправка в submitting запрещена, retry разрешён из error. Это предотвращает невозможные комбинации нескольких boolean-полей. Однако серверная идемпотентность всё равно нужна.

Антипаттерны: God component, глобальная шина без владельца/очистки, общий кэш без границы пользователя, бесконечный retry, абстракция с множеством исключений, распределённый монолит с синхронно сцепленными релизами. Их оцениваем по последствиям, не по эстетике.

**Практика:** API упал, каждый клиент делает немедленный retry. Объясни усиление сбоя, backoff с jitter, лимит попыток и ограничения повторов неидемпотентных операций.

## ARC-05. Как объяснить FSD и границы модулей?

**Ответ.** В FSD слои разделяют ответственность, slices группируют связанную предметную функциональность, segments — назначение кода внутри. Основные слои: app, pages, widgets, features, entities, shared. Не обязательно создавать все. Зависимости между slices в общем случае направлены вниз; публичный API ограничивает знание внутренних файлов. App/Shared имеют особую структуру; для связей entities есть явные cross-reference API.

**Пример.** Страница заказа собирает отображение сущности Order и действие отмены. Общая кнопка не знает о заказе. Единственный экранный блок без переиспользования можно оставить в странице: не всякая кнопка становится feature. Processes в текущей документации устарел.

**Практика:** feature A импортирует внутренний store feature B. Предложи поднять координацию выше, выделить общий смысл или пересмотреть неверно проведённую границу. Перемещение всего в shared не решает связанность.

## ARC-06. CSR, SSR, SSG, SPA и MPA — как выбирать?

**Ответ.** CSR строит интерфейс на клиенте; SSR генерирует HTML на сервере при запросе; SSG заранее генерирует HTML. SPA/MPA описывают характер навигации и документов, это другая ось: SPA может использовать SSR для первой загрузки. Hydration связывает серверную разметку с клиентским поведением и требует согласованного начального вывода.

| Сценарий | Возможный выбор | Цена |
|---|---|---|
| Закрытый кабинет | CSR | Зависимость первого UI от JS и запросов |
| Публичный меняющийся каталог | SSR с продуманным кэшированием | Сервер, нагрузка, hydration |
| Редко меняющиеся страницы | SSG | Время сборки и актуализация |

**Пример ошибки:** сервер выводит локальное время или случайное значение, клиент другое. Исправляем детерминированность и передачу начальных данных, а не отключаем предупреждения. **Практика:** выбери подход для каталога и кабинета одного продукта, учитывая SEO, персонализацию и стоимость.

## ARC-07. Cloud, S3, CDN, BFF и API — как связаны?

**Ответ.** Объектное хранилище держит объекты, CDN доставляет/кэширует, cloud предоставляет инфраструктурные сервисы. BFF адаптирует серверные контракты под конкретный клиент: агрегирует, нормализует и контролирует серверные credentials. Это дополнительный сервис с задержками, отказами и стоимостью поддержки.

**Пример.** Браузер загружает разрешённый файл по ограниченной подписанной ссылке, backend проверяет права и задаёт условия. Ссылка не заменяет валидацию содержимого. Для API нескольких клиентов изменения должны быть совместимыми: добавляем новое поле, мигрируем потребителей, только потом удаляем старое с согласованной политикой.

**Практика:** три сервиса формируют карточку заказа, один недоступен. Определи обязательные и необязательные данные, таймауты, частичный ответ и наблюдаемость. REST раскрывается здесь как прикладное дополнение к HTTP; отдельная строка REST в источнике находится в TODO.

## ARC-08. Как безопасно рефакторить и выделять библиотеку?

**Ответ.** Сначала фиксирую ожидаемое поведение и границы изменения, затем меняю небольшими шагами с проверкой значимых сценариев. Для библиотеки нужны несколько реальных потребителей, устойчивый публичный контракт, версия, миграция и владелец. Общий код без поддержки может дороже обойтись всем продуктам.

**Пример.** Перенос HTTP-клиента меняет трактовку 204: прежний код не читал JSON, новый пытается. Проверяем контракт пустого ответа, отмену, credentials, ошибки и retry. Снижение количества строк не доказывает сохранение поведения.

**Практика:** предложи план замены критичного модуля с постепенным включением, метриками, обратным переключением и условием удаления старого кода. ADR: контекст → варианты → решение → последствия.
