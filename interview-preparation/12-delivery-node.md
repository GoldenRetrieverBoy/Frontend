# Блок 12. Доставка, инфраструктура и Node.js

[План](README.md) · [Назад](11-tooling-git.md) · [Далее](13-performance-monitoring.md)

Команды и конфиги — учебные фрагменты, не поручение выполнить их в production. Они требуют соответствующей среды. SSR/BFF-часть условна по матрице; общую цепочку доставки разбираем в любом случае.

## OPS-01. Что нужно понимать в Linux и терминале?

**Ответ.** Процессы имеют окружение, права и потоки ввода/вывода; файлы — владельца и права чтения/записи/исполнения. Права каталога имеют иной смысл: execute позволяет проходить по пути. Код завершения используется скриптами для различения успеха и ошибки.

```sh
pwd
ls -l
curl -I https://example.com
rg 'error' app.log
```

rg — аналог задачи поиска grep; файл должен существовать. curl показывает поведение HTTP вне браузерной CORS-политики. SSH даёт удалённый сеанс с проверкой хоста и аутентификацией. Пакетный менеджер ОС отличается от npm: apt/apk устанавливают системные зависимости по правилам конкретного дистрибутива.

**Практика:** скрипт запускается локально, но получает permission denied в контейнере. Проверь пользователя, права файла/каталога, mount и интерпретатор; chmod 777 — не универсальное решение.

## OPS-02. Образ, контейнер и виртуальная машина — в чём разница?

**Ответ.** Образ — артефакт файловой системы и конфигурации запуска; контейнер — изолированное исполнение с процессами и собственным изменяемым слоем. Контейнеры обычно разделяют ядро хоста; VM имеет гостевую ОС/ядро. На macOS Linux-контейнеры работают через Linux-среду виртуализации.

```sh
docker login
docker pull nginx:stable
docker ps
docker exec <container> nginx -t
docker compose up -d
docker compose down
```

`<container>` — placeholder. login аутентифицирует в registry; pull получает образ; exec запускает команду в работающем контейнере. kill отправляет сигнал немедленного завершения по умолчанию; для штатной остановки нужно понимать stop и graceful shutdown. Удаление контейнера не равно удалению volume; down с отдельными флагами может удалить данные.

**Практика:** объясни, почему исправление файла внутри работающего контейнера пропало после пересоздания.

## OPS-03. Volumes, networks, registry и Compose — зачем?

**Ответ.** Volume отделяет срок жизни данных от контейнера; bind mount связывает путь хоста. Network даёт контейнерам связность и разрешение имён согласно настройке. Registry хранит/распространяет образы, tag — имя, которое может измениться, digest идентифицирует содержимое.

```yaml
# Фрагмент compose.yaml: image training-api должен существовать.
services:
  api:
    image: training-api:1
  web:
    image: nginx:stable
    ports:
      - "8080:80"
```

В сети Compose web может обращаться к api по имени сервиса и внутреннему порту, если API слушает соответствующий адрес. localhost внутри web означает сам web, а не api. Публикация порта хосту — отдельное действие; не все внутренние сервисы нужно публиковать.

**Практика:** браузер не разрешает имя api из Compose. Объясни различие DNS внутри сети контейнеров и адресов браузера пользователя.

## OPS-04. Как уменьшить образ и ускорить сборку?

**Ответ.** Разделяю build и runtime, копирую только нужные артефакты, исключаю лишний build context, использую кэш зависимостей и фиксирую подходящие версии. Измеряю отдельно холодную и повторную сборку, размер и время запуска.

```dockerfile
# Учебный пример. В реальном проекте фиксируем согласованные версии/digest.
FROM node:24-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:stable-alpine
COPY --from=build /app/dist /usr/share/nginx/html
```

Предполагаются lockfile, build script и dist. В .dockerignore включаем node_modules, .git и ненужные/чувствительные файлы. Исходники копируются после установки зависимостей, чтобы обычное изменение кода не сбрасывало этот кэш. Для SPA отдельно нужна маршрутизация NGINX. Dockerfile не включает полноценное production-hardening.

**Практика:** почему удаление большого файла в следующем слое не обязательно уменьшает уже созданные слои? Предложи не включать его в runtime вообще.

## OPS-05. Как строить CI/CD и разделять окружения?

**Ответ.** Pipeline делает воспроизводимые проверки и создаёт идентифицируемый артефакт; доставка продвигает его в окружение с понятной конфигурацией. Cache ускоряет повторную работу, artifacts передают результаты jobs. Нельзя считать кэш единственным источником обязательного результата.

```yaml
# Учебный GitLab CI: в package.json есть test:run и build.
image: node:24-alpine
stages: [test, build]
test:
  stage: test
  script:
    - npm ci
    - npm run test:run
build:
  stage: build
  script:
    - npm ci
    - npm run build
  artifacts:
    paths: [dist/]
```

Deploy здесь намеренно не выполняется: конкретные credentials и среда неизвестны. В интервью дополняем pipeline health-check, разрешениями, последовательностью релизов и rollback. Клиентские build-time env уже встроены в bundle; изменение env контейнера их автоматически не заменяет. Для одного образа на staging/production нужен продуманный runtime-config либо отдельные согласованные сборки.

**Практика:** старый pipeline завершился позже нового и перезаписал релиз. Предложи управление конкуренцией/устаревшими деплоями и проверку версии артефакта.

## OPS-06. Как NGINX отдаёт SPA и проксирует API?

**Ответ.** NGINX может отдавать статику и выступать reverse proxy. Для SPA URL клиентского маршрута часто должен вернуть index.html, а API и отсутствующий asset — свой корректный ответ. Общий fallback для всех путей маскирует ошибки HTML-ответом вместо JS/JSON.

```nginx
server {
  listen 80;
  root /usr/share/nginx/html;
  location /assets/ { try_files $uri =404; }
  location /api/ { proxy_pass http://api:3000; }
  location / { try_files $uri $uri/ /index.html; }
}
```

Это фрагмент без TLS и общей политики заголовков. proxy_pass без URI здесь сохраняет /api/ в пути upstream; наличие завершающего slash с URI может изменить преобразование пути. Проверяем конфигурацию nginx -t. Сжатие и кэширование настраиваем по типу ресурса, не для всего одинаково.

**Практика:** обновление /orders/123 даёт 404, переход внутри SPA работает. Затем другой случай: JS-запрос получает text/html. Объясни разные ошибки маршрутизации.

## OPS-07. Что нужно знать о Kubernetes для Mid3?

**Ответ.** Pod запускает контейнеры, Deployment управляет желаемыми репликами через контроллеры, Service даёт стабильный доступ к подходящим pod, ingress/controller или gateway организует внешний маршрут по принятой схеме. ConfigMap и Secret передают конфигурацию, но Secret не следует считать безопасным только из-за base64.

Readiness определяет готовность получать трафик; liveness может инициировать перезапуск; startup probe даёт приложению время стартовать. Ошибочная liveness при отказе зависимости может усилить аварию. Rolling update требует совместимости версий и корректной готовности.

```sh
kubectl get pods
kubectl describe pod <pod>
kubectl logs <pod>
kubectl rollout status deployment/<name>
```

Это read-only команды для разрешённого контекста; placeholders заменяются реальными именами. **Практика:** новый pod не готов. Различи image pull error, crash, неверную probe, порт, config и исчерпание ресурсов. Requests участвуют в планировании, limits ограничивают ресурсы; OOMKilled и CPU throttling имеют разные признаки.

## OPS-08. Зачем Frontend-разработчику Node.js?

**Ответ.** Для автоматизации, генерации и сборки Node предоставляет файловую систему, процессы и серверные API. Асинхронный I/O позволяет не ждать операцию в JS-потоке, но синхронная CPU-работа всё равно его занимает. Browser и Node event loop имеют разные детали; не переношу порядок всех очередей механически.

```js
import { readFile, writeFile } from 'node:fs/promises';
const pkg = JSON.parse(await readFile('package.json', 'utf8'));
await writeFile('build-info.json', JSON.stringify({ version: pkg.version }));
```

Пример выполняется как ES-модуль в учебном каталоге и создаёт файл. Для больших данных рассматриваем streams/backpressure вместо загрузки целого файла. Скрипт должен завершаться с ошибкой при обязательном неуспехе и не публиковать env целиком.

**Практика:** генератор начал потреблять гигабайты памяти. Найди чтение целого набора, неограниченную конкурентность и удержание промежуточных объектов.

## OPS-09. Условный блок: SSR/BFF, кэш, профилирование памяти

**Ответ.** Серверный процесс обслуживает многих пользователей, поэтому состояние запроса и персональный кэш должны иметь явные границы. Ключ, TTL, инвалидирование и максимальный размер — части контракта кэша. У SSR есть стоимость рендера, ожидание API, таймауты и согласование HTML/состояния клиента.

**Пример.** Кэш по URL /profile без userId может вернуть чужие данные. Глобальный массив request-логов растёт бесконечно. В диагностике сравниваю heap, RSS, нагрузку и длительность, смотрю удерживающие ссылки и CPU-профиль. Снятие heap snapshot может быть ресурсоёмким: процедуру выбираем с учётом среды.

**Практика:** SSR медленнее после нескольких часов. Раздели рост очереди, утечку памяти, GC и внешнюю зависимость. Для метрик/логов продолжи блок 13.
