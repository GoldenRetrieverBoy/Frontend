## NET-01. Что происходит после ввода URL? Где DNS, TCP и TLS?

**Ответ.** Браузер разбирает URL, учитывает локальные кэши и политики, получает адрес через разрешение имени, устанавливает или переиспользует соединение, выполняет защищённое согласование для HTTPS, отправляет HTTP-запрос и обрабатывает ответ. Не каждый переход повторяет все этапы: соединение и DNS-результат могут быть закэшированы.

DNS сопоставляет имена с записями: A/AAAA дают адреса, CNAME — другое имя; рекурсивный resolver обращается к нужным серверам, TTL ограничивает срок кэширования. HTTP/1.1 и HTTP/2 обычно используют TCP; HTTP/3 — QUIC поверх UDP, поэтому «любой HTTPS сначала делает TCP-handshake» неверно.

OSI — концептуальная модель: физический, канальный, сетевой, транспортный, сеансовый, представления, прикладной уровни. Для диагностики важнее связать IP, транспорт, TLS и HTTP, чем механически перечислить слои.

**Практика:** один домен не открывается, другой работает. Раздели проверку DNS, соединения, сертификата и HTTP-ответа; не называй всякую недоступность CORS.

## NET-02. Чем TCP отличается от UDP и где WebSocket?

**Ответ.** TCP предоставляет упорядоченный поток байтов с механизмами надёжной доставки и управления потоком/перегрузкой. UDP передаёт датаграммы без тех же гарантий доставки и порядка; протокол поверх UDP может добавить нужные гарантии. WebSocket даёт двусторонний обмен сообщениями поверх длительного соединения.

**Пример.** Для уведомлений WebSocket требует reconnect, проверки доступности, восстановления пропущенных событий и ограничений очередей. Сам reconnect не восстанавливает историю. Можно передавать lastEventId и запрашивать пропущенное в прикладном протоколе.

**Практика:** спроектируй обновление статуса заказа при разрыве сети на минуту. **Уточнение:** почему WebSocket не всегда лучше polling? Появляются стоимость соединений, инфраструктура и сложность восстановления; редкие обновления могут не оправдывать это.

## NET-03. Как устроен HTTP-запрос, методы и статусы?

**Ответ.** Запрос содержит метод, целевой ресурс, заголовки и иногда тело; ответ — статус, заголовки и тело. Safe-метод по смыслу не запрашивает изменение состояния сервера; идемпотентность означает одинаковый предполагаемый эффект повторений, а не идентичный ответ.

```http
POST /orders HTTP/1.1
Host: example.test
Content-Type: application/json
Idempotency-Key: example-request-123

{"offerId":"offer-1"}
```

GET — чтение; POST часто создаёт или выполняет операцию; PUT задаёт представление ресурса; PATCH частично меняет, но не гарантированно идемпотентен; DELETE идемпотентен по смыслу удаления. 201 — создание, 204 — без содержимого, 400 — некорректный запрос, 401 — требуется подходящая аутентификация, 403 — отказ в доступе, 409 — конфликт, 429 — ограничение частоты, 5xx — серверная ошибка. fetch обычно не отклоняет Promise просто из-за 404/500: проверяем ok/status.

**Практика:** запрос создания заказа завершился таймаутом. Почему повтор опасен? Сервер мог создать заказ, но ответ потерялся. Idempotency-Key помогает только если сервер реализует его контракт.

## NET-04. Как работают HTTP-кэш и CDN?

**Ответ.** Fresh-ответ может использоваться без повторного запроса; stale-ответ в зависимости от политики перепроверяется. ETag/If-None-Match позволяют получить 304 без полного тела. no-cache означает необходимость проверки перед повторным использованием, no-store — запрет хранения данным кэшем. CDN размещает кэш и доставку ближе к пользователям, но не гарантирует hit.

```http
Cache-Control: public, max-age=31536000, immutable
```

Это подходит контентно-версионированному публичному asset, например app.abc123.js. HTML с указателем на новый asset требует иной политики, например проверки актуальности. Для персональных ответов учитываем private/no-store и ключ кэша; Vary расширяет различение вариантов, но высокое разнообразие уменьшает hit rate.

**Практика:** после релиза HTML ссылается на удалённый старый chunk. Предложи совместимую доставку: сохранение предыдущих assets, версионирование, атомарное переключение, проверка кеширования HTML.

## NET-05. Что такое CORS и preflight?

**Ответ.** Same-origin policy ограничивает доступ скрипта к данным другого origin. Origin включает схему, хост и порт. CORS — серверный способ разрешить браузеру определённый междоменный доступ. Preflight OPTIONS проверяет разрешения для запросов с несоответствующими safelist методом/заголовками/типом содержимого.

```js
fetch('https://api.example.test/profile', { credentials: 'include' });
```

Для credentialed CORS сервер должен разрешить конкретный origin, а не `*`, и credentials; применяются также правила cookies и браузера. CORS не является аутентификацией и не запрещает curl обращаться к серверу. Некоторые запросы отправляются даже когда браузер не разрешит прочитать ответ. Поэтому CORS не заменяет CSRF-защиту.

**Практика:** POST JSON не отправляется после OPTIONS. Проверь запрошенные метод/заголовки и CORS-ответ, затем маршрутизацию OPTIONS. `mode:'no-cors'` не даёт читать произвольный ответ.

## NET-06. Content-Type, multipart, cookies и HTTPS — что важно?

**Ответ.** Content-Type описывает представление тела; Accept — желаемые типы ответа. Multipart разделяет несколько частей boundary, например файл и поля. При FormData браузер сам формирует Content-Type с boundary: вручную ставить голый multipart/form-data не нужно.

```js
const body = new FormData();
body.append('title', 'Документ');
// file — File, выбранный пользователем.
body.append('file', file);
fetch('/upload', { method: 'POST', body });
```

Cookies имеют область Domain/Path, срок, Secure, HttpOnly и SameSite. HttpOnly ограничивает чтение из JS, но не автоматически предотвращает выполнение запросов через XSS. HTTPS обеспечивает защищённый канал и проверку серверной стороны по сертификату; не исправляет логические уязвимости приложения.

**Практика:** cookie установлена, но не приходит на API. Проверяй область, Secure, SameSite, credentials, срок и ограничения браузера, а не только содержимое Application tab.
