## PERF-01. Как искать медленный участок?

**Ответ.** Сначала определяю сценарий, условия и метрику, воспроизвожу, записываю профиль, формирую гипотезу, меняю одну существенную причину и повторяю измерение. DevTools Network показывает загрузку, Performance — работу во времени, Memory — удержание объектов, Debugger — состояние выполнения.

**Пример.** Поиск кажется медленным: API отвечает за 100 мс, но затем главный поток 800 мс строит список. Оптимизация API на 20 мс почти не изменит ощущение. Проверяем long tasks, пересчёты и DOM. В debugger используем breakpoint, conditional breakpoint, pause on exceptions и async stack; логирование не единственный метод.

**Практика:** запиши план измерений на замедленном CPU и сети, но отдельно проверь реальные пользовательские устройства. **Ошибка:** сравнивать один холодный запуск с одним прогретым.

## PERF-02. Что измеряют LCP, INP и CLS?

**Ответ.** LCP отражает момент появления крупнейшего подходящего видимого содержимого; INP — отзывчивость взаимодействий за посещение по своей методике; CLS — неожиданные сдвиги расположения. Это разные проблемы: загрузка, взаимодействие, стабильность.

Ориентиры хорошего опыта: LCP ≤2,5 с, INP ≤200 мс, CLS ≤0,1, оценка по 75-му перцентилю соответствующих посещений. Это не гарантия качества каждого пользователя. INP заменил FID в Core Web Vitals в 2024 году.

**Пример.** LCP: позднее hero-изображение; INP: долгий обработчик фильтра; CLS: изображение без зарезервированного размера. **Практика:** для каждого выбери одну гипотезу и проверяемое изменение. **Ошибка:** применять lazy loading к главному изображению, пытаясь улучшить LCP.

## PERF-03. Lab/field, TTFB, FCP, TBT и TTI — зачем знать?

**Ответ.** Lab даёт контролируемый воспроизводимый эксперимент, field — реальные условия посещений. TTFB связан с ожиданием первого байта, FCP — первого содержимого, TBT в лабораторном сценарии суммирует блокирующие части длинных задач в определённом интервале. TTI — историческая метрика готовности к взаимодействию; её наличие и использование зависят от инструмента. TBT не равен INP.

**Пример.** Lighthouse хороший, field плохой: другие устройства, сеть, посещаемые маршруты, долгие сессии и реальные действия. Сегментируем, а не объявляем один источник неправильным. В матрице эта детализация частично Senior; включаем как дополнение для корректного понимания диагностики Mid3.

**Практика:** объясни, почему среднее скрывает медленный хвост, и выбери размер/период выборки перед сравнением релизов.

## PERF-04. Как ускорить ресурсы, список и рендер?

**Ответ.** Уменьшаю объём ненужной работы: подходящие размеры/форматы изображений, поднаборы и загрузку шрифтов, code splitting, сжатие текста, кэширование, отложенную загрузку второстепенного. gzip/Brotli уменьшают передачу, но не убирают стоимость исполнения JS. Сжатие уже сжатых изображений часто мало помогает.

**Пример.** Пагинация ограничивает данные страницами; infinite scroll меняет подгрузку, но сам не ограничивает накопленный DOM; виртуализация держит небольшое окно элементов и требует учёта высот, фокуса и доступности. Для списка 50 000 строк одной memoization недостаточно, если всё равно создаются 50 000 DOM-поддеревьев.

**Практика:** выбери между пагинацией и виртуализацией для таблицы с поиском, печатью и клавиатурой. Объясни компромиссы, а не только скорость.

## PERF-05. Как использовать Sentry и логи ELK?

**Ответ.** Ошибка полезна вместе с release, окружением, маршрутом, техническими тегами и предшествующими событиями. Source maps помогают восстановить исходный stack. Breadcrumbs дают последовательность событий, cause — связь ошибок. Логи описывают отдельные события; метрики удобны для агрегированного состояния.

**Пример расследования.** Выбираю регрессию по времени и release, оцениваю затронутых пользователей, группирую по маршруту/браузеру, сопоставляю request/trace id с серверными логами. В Kibana уточняю схему индекса и язык запроса, затем фильтрую время, окружение и статус; имена полей не универсальны.

```text
Пример KQL при наличии этих полей:
service.name: "frontend" and http.response.status_code >= 500
```

Уровни debug/info/warn/error должны отражать смысл, а не использовать error для всего. Токены и персональные payload не должны автоматически попадать в context. **Практика:** «Cannot read properties of undefined» без release и source maps — какие сведения добавишь и почему?

## PERF-06. Как проектировать Grafana dashboard и alert?

**Ответ.** Dashboard отвечает на вопрос о состоянии системы, alert — требует конкретного действия. Для алерта задаю источник, выражение, порог/окно, минимальный объём данных, обработку no data, маршрут уведомления и runbook. No data не всегда означает здоровье.

**Пример.** Отслеживаем долю ошибок оформления: число неуспешных попыток / все попытки по согласованному определению. Рядом — интенсивность и latency; рост с 0 до 1 ошибки при 1 запросе не трактуем как массовую аварию без контекста. Добавляем release annotation и владельца реакции.

**Практика:** составь dashboard из 4 панелей и один actionable alert. Объясни, что делать получателю в первые пять минут. **Ошибка:** уведомлять о каждой отдельной ошибке без группировки и связи с воздействием.

## PERF-07. Условный блок: Graphite и серверные метрики

**Ответ.** Graphite принимает, хранит и позволяет запрашивать числовые временные ряды; Grafana может визуализировать данные источника. Сбор метрики выполняет приложение/агент, наличие Grafana само по себе ничего не измеряет. Выбираем единицы, интервалы и агрегацию: скорость запросов, ошибки, длительность, память.

**Пример.** `training.bff.requests` и `training.bff.memory_bytes` имеют разный смысл агрегации. Для счётчика нужна корректная обработка сброса/скорости, для памяти — уровень во времени. userId/orderId в имени ряда создаёт неограниченную кардинальность. Локальные p95 разных инстансов нельзя просто усреднить и назвать общим p95.

**Практика:** опиши путь метрики от Node-сервиса до панели и поведение при остановке отправки. Условие из матрицы: наличие Node.js-бэкенда.
