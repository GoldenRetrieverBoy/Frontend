## TOOL-01. Зачем package manager и lockfile?

**Ответ.** Менеджер пакетов разрешает зависимости, скачивает их и связывает доступные пакеты. package.json задаёт намерение и диапазоны, lockfile фиксирует разрешённый граф и связанные данные для воспроизводимой установки. Воспроизводимость также зависит от версии среды, платформы и install scripts.

```sh
npm ci
npm ls
npm explain some-package
```

Это учебные команды: some-package заменяем реальным пакетом. npm ci рассчитан на установку по согласованному lockfile и удаляет существующий node_modules; это не обычное добавление пакета. dependencies нужны потребителям/исполнению по контракту пакета, devDependencies — разработке и сборке; peerDependencies задают совместимость с зависимостью окружения потребителя. В статической SPA браузер получает bundle, а не читает эти разделы.

**Практика:** локально сборка проходит, в CI нет. Сравни Node/package manager, lockfile, env, регистр путей и scripts. **Ошибка:** лечить проблему удалением lockfile без анализа изменений графа.

## TOOL-02. Как работает bundler и чем dev отличается от build?

**Ответ.** Сборщик строит граф модулей, преобразует исходники и ресурсы, оптимизирует и формирует выходные файлы. Dev-сервер делает акцент на быстром обновлении и диагностике; production-сборка — на распространяемых артефактах. Названия внутренних движков Vite зависят от версии, поэтому на интервью отделяю архитектурную идею от версии реализации.

**Пример.** Импорт тяжёлого отчёта через dynamic import создаёт возможность отдельной загрузки. Tree shaking убирает доказуемо ненужный код при подходящей структуре модулей и учёте side effects; минификация только уменьшает представление. Source maps связывают результирующий JS с исходником.

**Практика:** найти пакет, который увеличил initial bundle, и проверить граф импортов. **Уточнение:** почему dev работает, build падает? Различаются env, преобразования, пути, оптимизации; типы могут проверяться отдельной командой.

## TOOL-03. Как оптимизировать bundle и писать плагин?

**Ответ.** Сначала измеряю исходный/сжатый размер и реальную стоимость загрузки/исполнения. Затем смотрю дубли зависимостей, широкие импорты, локали, статические ресурсы и границы ленивой загрузки. Больше чанков не всегда лучше: есть накладные расходы и риск waterfall.

```js
// Учебный Vite-плагин: добавляет метку в HTML.
export default {
  plugins: [{
    name: 'build-label',
    transformIndexHtml(html) {
      return html.replace('</head>', '<meta name="build-kind" content="training"></head>');
    },
  }],
};
```

Пример предполагает Vite config с HTML-entry. Для реального плагина выбираем API нужной версии, проверяем dev/build, sourcemaps при трансформациях JS и отсутствие секретов. Для генерации константы существующий механизм config может быть проще собственного плагина.

**Практика:** общий vendor chunk вырос до нескольких мегабайт. Реши, какие зависимости нужны первой странице, а какие только отчёту, и проверь Network после разделения.

## TOOL-04. Зачем линтер и monorepo?

**Ответ.** Линтер проверяет договорённости и потенциальные ошибки; type checker проверяет типовые отношения; formatter — оформление. Они решают разные задачи. Monorepo объединяет проекты в одном репозитории, но требует управлять графом пакетов, публичными API, задачами, версиями и кэшем сборок.

**Пример.** Два приложения используют UI-kit. Изменение токена должно перезапустить затронутые проверки; кэш обязан учитывать входы, lockfile и значимые env. Неверный cache key может вернуть успешный, но чужой артефакт. Turborepo/Lerna — инструменты, а не обязательная архитектура любого репозитория.

**Практика:** введи правило запрета внутреннего импорта библиотеки и план постепенного исправления старых нарушений. **Ошибка:** включить множество правил без объяснения и оставить массовые disable.

## TOOL-05. Что хранит Git и чем reset отличается от revert?

**Ответ.** Коммит описывает снимок и родителей; ветка — перемещаемая ссылка, HEAD — текущая точка. Рабочее дерево, index и история — разные состояния. reset передвигает ссылку и в зависимости от режима меняет index/рабочее дерево. revert добавляет обратное изменение новым коммитом и обычно удобнее для опубликованной общей истории.

```sh
git status --short
git diff
git diff --staged
git log --oneline --graph -10
git diff main...feature
```

Последняя команда показывает изменения feature относительно общего предка при существующих refs. clone создаёт локальную копию, add готовит index, commit фиксирует, fetch обновляет удалённые refs, pull дополнительно интегрирует, push публикует. SSH обеспечивает транспортную аутентификацию; приватный ключ не передают в репозиторий.

**Практика:** случайно добавлен debug-код, остальное нужно сохранить. Назови состояние изменения и точечный способ убрать его. Не предлагай reset --hard без оценки потери данных.

## TOOL-06. Merge, rebase и cherry-pick — как выбрать?

**Ответ.** Merge объединяет линии истории, rebase воспроизводит изменения на другой базе и создаёт новые коммиты, cherry-pick переносит выбранное изменение. При конфликте нужно восстановить смысл обоих изменений, а не автоматически выбрать ours/theirs.

**Пример.** Hotfix нужен в release и develop: выбираем перенос с учётом процесса, затем проверяем, что логика не дублируется при следующем merge. Rebase опубликованной ветки требует координации, поскольку меняет идентификаторы. Reflog может помочь найти потерянную локальную точку, но не заменяет резервирование.

**Практика:** два разработчика изменили один API-контракт. Опиши чтение обеих версий, согласование итогового типа, тесты потребителей и завершение конфликта.

## TOOL-07. GitFlow, Trunk Based и GitLab — что проверят у Middle 3?

**Ответ.** GitFlow использует отдельные долгоживущие ветки и релизные потоки; Trunk Based опирается на частую интеграцию небольших изменений и обычно короткие ветки. Выбор зависит от релизов и проверки, а не от моды. Feature flags отделяют интеграцию кода от доступности функции, но требуют удаления устаревших флагов.

GitLab MR — площадка проверки изменения; управление репозиторием включает защищённые ветки, права, owners и правила интеграции. Webhook отправляет события внешней системе; получатель проверяет подлинность по возможностям интеграции и обрабатывает дубли/повторы. Успешный HTTP webhook ещё не означает бизнес-успех обработки.

**Практика:** предложи правила MR для общей библиотеки: потребители, совместимость, проверки, выпуск версии, миграция. **Ошибка:** выдавать широкие права ради обхода падающей проверки.
