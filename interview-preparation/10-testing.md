## TEST-01. Какие тесты выбрать и что такое тестируемый код?

**Ответ.** Выбираю уровень по риску: unit проверяет локальную логику, integration — взаимодействие частей, component — поведение компонента в заданном окружении, end-to-end — пользовательский путь через систему. Границы названий в командах различаются, поэтому уточняю, что реально включено в тест.

**Пример.** Формула скидки — быстрый unit; форма с валидацией и отправкой — component/integration; успешное оформление заказа — небольшой набор E2E. Тестируемый код имеет явные входы/выходы, контролируемые время и зависимости, отделённые эффекты.

**Практика:** распределить риски оплаты между уровнями и назвать то, что нельзя доказать браузерным тестом с полностью замоканным backend.

## TEST-02. Что такое mock, stub, spy и fixture?

**Ответ.** Fixture готовит входы и окружение; stub возвращает заданный ответ; spy фиксирует вызовы; mock часто объединяет управляемую замену и проверку взаимодействия. Важнее согласованный контракт теста, чем спор о названии.

```ts
import { expect, it, vi } from 'vitest';
it('уведомляет после сохранения', async () => {
  const save = vi.fn().mockResolvedValue({ id: '1' });
  const notify = vi.fn();
  const order = await save();
  notify(order.id);
  expect(notify).toHaveBeenCalledWith('1');
});
```

Это демонстрация API spy, не полноценный тест бизнес-функции: в настоящем тесте вызывается production-сценарий, а не его копия внутри it. Не следует мокать каждую внутреннюю функцию: тест начинает подтверждать собственные ожидания вместо интеграции.

**Практика:** выбери одну границу замены для формы: HTTP или composable, и объясни, какие ошибки второй подход может скрыть.

## TEST-03. Что показывает coverage?

**Ответ.** Покрытие показывает, какие строки/ветви/функции исполнялись, а не насколько верны проверки. 100% строк не доказывают правильность результата, полноту требований или проверку границ. Использую coverage как сигнал непройденных ветвей вместе с анализом рисков.

```ts
import { expect, it } from 'vitest';
const canCancel = (status: string) => status === 'draft';
it.each([
  ['draft', true], ['paid', false], ['cancelled', false],
])('отмена для %s', (status, expected) => {
  expect(canCancel(status)).toBe(expected);
});
```

Параметризация убирает повтор тестового сценария, сохраняя понятные случаи. **Практика:** для ограничения «до 10 включительно» проверь 9, 10, 11 и недопустимые входы согласно контракту. **Ошибка:** единственная проверка «не бросает исключение» для расчётной функции.

## TEST-04. Как тестировать async и таймеры без flaky-тестов?

**Ответ.** Ожидаю наблюдаемое завершение операции, а не случайный sleep. Управляю таймерами и Promise на границах. После теста восстанавливаю окружение; очищаю моки, подписки и компоненты, чтобы тесты не зависели друг от друга.

```ts
import { expect, it, vi } from 'vitest';
it('вызывает обработчик по таймеру', () => {
  vi.useFakeTimers();
  try {
    const fn = vi.fn();
    setTimeout(fn, 100);
    vi.advanceTimersByTime(99);
    expect(fn).not.toHaveBeenCalled();
    vi.advanceTimersByTime(1);
    expect(fn).toHaveBeenCalledTimes(1);
  } finally { vi.useRealTimers(); }
});
```

В смешанном async-коде могут понадобиться асинхронные методы продвижения таймеров и ожидание Promise. Vue nextTick ждёт обновление Vue, а не произвольный сетевой Promise.

**Практика:** управляемыми Promise заверши второй поиск раньше первого и докажи, что первый не перезаписывает данные и loading. **Ошибка:** чинить flaky-тест увеличением sleep без поиска причины.

## TEST-05. Что проверять в компоненте?

**Ответ.** Контракт пользователя и родителя: видимый текст, состояния, доступные действия, события и payload. Выбор реализации store или название внутреннего метода обычно не должны ломать тест поведения.

**Пример.** Вводим email, отправляем форму, видим loading, затем успех. Отдельно проверяем ошибку, повторную отправку, клавиатуру и отсутствие события при невалидных данных. DOM-эмулятор не воспроизводит реальную геометрию и всё браузерное поведение; layout и фокус сложного диалога проверяем в браузере.

**Практика:** составь 5 проверок формы заказа и объясни, почему огромный snapshot всей разметки слабее целевых утверждений. Для селекторов сначала доступны роли/имена; устойчивый test id полезен там, где семантика не различает элементы.

## TEST-06. Как проводить нагрузочное тестирование?

**Ответ.** Сначала определяю цель и модель нагрузки: сценарии, интенсивность, конкурентность, данные, длительность, прогрев и критерии остановки. Смотрю throughput, ошибки, p95/p99, ресурсы и насыщение. Нагрузка на HTTP API и измерение отзывчивости браузера — разные проверки.

**Пример.** При росте запросов с 20 до 100 в секунду p95 растёт, CPU низкий, пул соединений исчерпан. Увеличение CPU не обязательно поможет. Проверяем зависимость и очередь, не делаем вывод только по среднему времени.

**Практика:** опиши тест SSR-каталога в изолированной среде: ожидаемый профиль трафика, лимиты, серверные метрики, ошибки и параллельный browser trace. Добавь сравнение до/после в одинаковых условиях.
