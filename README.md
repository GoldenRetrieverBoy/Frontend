# Performance Review Tracker

Персональный проект для систематического сбора информации о моей работе, импакте и достижениях. Используется для подготовки к performance review (каждые 6 месяцев) и демо в конце каждого спринта.

---

## Зачем этот проект

Performance review — это момент, когда нужно защитить свой импакт за полугодие. Проблема в том, что к моменту ревью большая часть деталей забывается. Этот проект решает эту проблему: информация записывается по горячим следам и структурируется так, чтобы в конце полугодия осталось только собрать итоговый документ.

Второе применение — подготовка к demo в конце спринта. Каждое demo хранится отдельным файлом внутри полугодия и месяца; там фиксируются scope, run of show, заметки и feedback.

### Описание файлов

#### `sprints/sprint-XX.md` — спринтовый файл

Основной рабочий файл. Заполняется каждый спринт по горячим следам. Содержит:

- **Задачи и результаты** — таблица с задачами, типом (feature/bugfix/improvement/infra), статусом и импактом
- **Связанные demo** — ссылки на отдельные demo-файлы периода
- **Ключевые достижения** — что важного произошло в этом спринте
- **Метрики спринта** — количество PR-ов, задач, багов
- **Техническое** — технологии, архитектурные решения, работа с техдолгом
- **Коллаборация** — помощь коллегам, код-ревью, менторинг, полученная обратная связь

#### `metrics.md` — метрики полугодия

Агрегированные числа за весь период. Таблица по месяцам с ключевыми метриками: задачи, PR-ы, фичи, баги, инциденты. Также секции для перформанс-метрик (скорость, оптимизации), покрытия тестами, uptime/SLA.

Обновляется по мере накопления данных, минимум раз в месяц.

#### `demos/YYYY-MM/X.Y.Z.md` — demo-файл

Отдельный файл для каждого demo внутри соответствующего полугодия и месяца. Содержит Inbox заметок, narrative, run of show, capability impact, ожидаемый эффект и feedback после показа.

#### `highlights.md` — топ достижений

5–10 главных достижений за полугодие в формате:

> **Что сделал** → **Какой результат / импакт (с цифрами)**

Это выжимка, которая идёт прямо в ревью. Обновляется при появлении значимого достижения.

#### `summary.md` — итоговый документ для ревью

Финальный документ, который используется для защиты на performance review. Собирается в конце полугодия из highlights и metrics. Структурирован по категориям импакта:

- Технический импакт (проекты, фичи, качество, архитектура)
- Продуктовый импакт (влияние на продукт, пользователей, бизнес-метрики)
- Командная работа и лидерство (ревью, менторинг, инициативы)
- Обратная связь
- Зоны роста и цели

## Рабочие процессы

### Каждый спринт

1. Скопировать `templates/sprint-template.md` → `HX-YYYY/sprints/sprint-XX.md`
2. В начале спринта заполнить даты
3. В течение спринта записывать задачи по мере их завершения
4. Перед demo добавить ссылку на файл из `demos/YYYY-MM/`
5. После demo записать feedback в отдельном demo-файле
6. В конце спринта заполнить метрики и заметки

### Перед и после demo

1. Создать `HX-YYYY/demos/YYYY-MM/X.Y.Z.md` из `templates/demo-template.md`
2. В течение спринта складывать сырые заметки в Inbox
3. Перед показом собрать narrative и run of show
4. После demo записать feedback, решения и follow-up
5. Перенести подтверждённый delivery в highlights, а измеренный эффект — в metrics

**Совет:** лучше записывать сразу как сделал задачу, а не в конце спринта. Так детали точнее.

### Раз в месяц

1. Обновить `metrics.md` — добавить числа за прошедший месяц
2. Посмотреть, есть ли что добавить в `highlights.md`
3. Если было значимое достижение — записать сразу

### Перед performance review

1. Перечитать все спринтовые файлы за полугодие
2. Убедиться что `metrics.md` актуален
3. Убедиться что `highlights.md` содержит 5–10 лучших достижений
4. Собрать `summary.md` из highlights и metrics
5. При необходимости выгрузить данные из Asana для уточнения метрик

### Новое полугодие

1. Создать папку `HX-YYYY/` (например `H1-2027/`)
2. Создать в ней подпапки `sprints/` и `demos/`
3. Создать `demos/README.md` как индекс demo нового полугодия
4. Скопировать и адаптировать `metrics.md`, `highlights.md`, `summary.md` из шаблонов или предыдущего полугодия

## Правила заполнения

### Конкретность

Не «улучшил производительность», а «ускорил загрузку дашборда с 3с до 0.8с». Не «закрыл много задач», а «закрыл 23 задачи на 47 SP».

### Цифры

Указывай цифры везде где возможно:

- Story points
- Количество задач, PR-ов
- Процент улучшения (было X → стало Y, −Z%)
- Денежный эффект (экономия ~N тг)
- Временной эффект (было 7 мин → стало 3 мин)

### Формат импакта

Для каждого значимого достижения фиксируй четыре аспекта (формат из ревью):

1. **Импакт на бизнес** — почему это важно для компании
2. **Проблема** — что было до твоего вмешательства
3. **Действия** — что конкретно ты сделал
4. **Результат** — измеримый результат с метриками

### Обратная связь

Записывай фидбек от коллег и менеджера сразу как получил. Прямые цитаты ценнее пересказа.

### Лучше больше, чем меньше

Записать лишнее проще, чем вспомнить забытое через 5 месяцев.

## Интеграция с Asana

Проект может использовать данные из Asana для уточнения метрик и сбора задач. При подготовке к ревью или заполнении спринтов можно:

- Выгрузить завершённые задачи за период
- Посчитать количество задач по типам
- Собрать задачи с датами completion для timeline
- Уточнить story points по задачам

Выгрузка делается через Claude с подключённым Asana-коннектором.

## Категории импакта для ревью

При заполнении summary ориентируйся на эти категории:

| Категория | Что включать |
|-----------|-------------|
| Технический импакт | Фичи, архитектура, техдолг, оптимизации, надёжность |
| Продуктовый импакт | Влияние на пользователей, бизнес-метрики, конверсии, revenue |
| Операционный импакт | Автоматизация, сокращение ручной работы, ускорение процессов |
| Team-level импакт | Инструменты для команды, менторинг, инициативы |
| Командная работа | Код-ревью, помощь коллегам, документация |

---

## Типы задач

При заполнении спринтовых файлов используй эти типы:

| Тип | Описание |
|-----|----------|
| `feature` | Новая функциональность |
| `bugfix` | Исправление бага |
| `improvement` | Улучшение существующего |
| `infra` | Инфраструктура, CI/CD, зависимости |
| `platform` | Платформенные изменения, codegen, либы |
| `refactor` | Рефакторинг без изменения поведения |
| `docs` | Документация |
