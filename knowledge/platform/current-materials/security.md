# Блок 07. Безопасность

[План](../README.md) · [Назад](../platform/networking.md) · [Далее](../engineering/architecture.md)

Сценарии — для анализа собственного приложения и учебной среды. Здесь проверяется понимание механизма защиты и границ доверия.

<a id="sec-01"></a>

## SEC-01. Что такое XSS и как защититься?

**Ответ.** XSS возникает, когда недоверенные данные становятся исполняемым содержимым в контексте приложения. Защита зависит от места вставки: текст, HTML, URL, JavaScript имеют разные правила. Предпочитаю безопасные DOM API и обычную текстовую интерполяцию. Для разрешённого HTML нужна поддерживаемая санитизация с подходящей политикой.

```js
// element и userText получены приложением.
element.textContent = userText; // отображение текста
// element.innerHTML = userText; // опасный sink для недоверенного HTML
```

Vue интерполяция текста экранирует его; v-html обходит эту защиту. CSP добавляет слой ограничения выполнения, но не заменяет корректную обработку данных. Проверка «нет тега script» не защищает от всех способов исполнения.

**Практика:** редактор описаний поддерживает ссылки и жирный текст. Определи разрешённые элементы/атрибуты/URL-схемы и место санитизации. **Уточнение:** почему HttpOnly не делает XSS безвредной? Вредоносный JS может действовать в текущей сессии без чтения cookie.

<a id="sec-02"></a>

## SEC-02. Аутентификация, авторизация и CSRF — чем различаются?

**Ответ.** Аутентификация устанавливает личность, авторизация проверяет право на действие и объект. CSRF использует автоматически прикладываемые браузером credentials для нежелательного действия с другого сайта. Сервер проверяет права на каждый защищённый ресурс; скрытая кнопка не является контролем доступа.

**Пример.** Пользователь меняет orderId в запросе. Сервер должен проверить принадлежность заказа. Для cookie-сессии выбираем CSRF-токен и/или проверку origin и другие подходящие меры вместе с SameSite. SameSite различает site, а не строго origin; поддомены могут быть same-site.

**Практика:** составь проверки для отмены заказа: личность, право на конкретный заказ, допустимый статус, CSRF и повтор операции. **Ошибка:** «CORS не пустит злоумышленника, поэтому серверная проверка не нужна».

<a id="sec-03"></a>

## SEC-03. JWT, OAuth, OIDC и SSO — одно и то же?

**Ответ.** JWT — формат токена с claims; распространённый подписанный JWT не скрывает содержимое. OAuth — протокол делегированной авторизации; OIDC добавляет идентификационный слой. SSO — возможность единого входа в несколько систем, реализуемая разными протоколами. Проверка подписи, issuer, audience и срока нужна на доверенной стороне; декодирование payload не равно проверке.

**Пример.** SPA перенаправляет пользователя к провайдеру, получает authorization code и использует поток с PKCE согласно архитектуре клиента. Нельзя класть client secret в публичный JS. Для BFF можно оставить серверные токены на сервере, а браузеру дать сессию; это меняет риски, а не устраняет все из них.

**Практика:** 20 запросов получили 401 одновременно. Опиши единственный refresh в процессе, ожидание остальных, ограничение повторов и выход при окончательном отказе. **Ошибка:** бесконечный цикл refresh → retry → 401.

<a id="sec-04"></a>

## SEC-04. Что дают CSP и security headers?

**Ответ.** CSP ограничивает источники и способы загрузки/исполнения содержимого. Nonce/hash позволяют разрешить ожидаемые скрипты без общего unsafe-inline; политика должна соответствовать приложению. HSTS закрепляет HTTPS для хоста по правилам браузера, nosniff ограничивает MIME-sniffing, Referrer-Policy управляет отправкой referrer, frame-ancestors ограничивает встраивание.

```http
Content-Security-Policy-Report-Only: default-src 'self'; object-src 'none'; base-uri 'self'
```

Это пример начального наблюдения, а не готовая универсальная production-политика; Report-Only не блокирует. Перед enforcing анализируем нарушения и необходимые интеграции. X-Frame-Options полезно понимать исторически; X-XSS-Protection устарел и не предлагается как основная защита.

**Практика:** политика сломала оплату во внешнем iframe. Разбери конкретную директиву и минимально необходимое разрешение вместо удаления CSP целиком.

<a id="sec-05"></a>

## SEC-05. Как защититься от перебора и утечки секретов?

**Ответ.** Ограничения частоты и попыток реализуются на серверной стороне с учётом аккаунта, источника, распределённого трафика и риска блокировки легитимных пользователей. CAPTCHA — дополнительный сигнал, клиентский setTimeout легко обойти. Ошибки входа не должны без необходимости раскрывать существование аккаунта.

**Пример.** Секрет, переданный в переменную клиентской сборки, оказывается доступен пользователю после подстановки в JS. Скрыть его минификацией невозможно. В логах не сохраняем Authorization и содержимое сессионных cookies. Маскирование CI не заменяет ограничение прав и доверенных запускающих субъектов.

**Практика:** токен оказался в публичном bundle. План: отозвать/заменить, устранить канал публикации, оценить использование, проверить артефакты и историю. Простого удаления строки из текущего кода недостаточно.

## SEC-06. Что входит в OWASP Top 10:2025?

**Ответ.** Это перечень крупных классов рисков, а не полный тест-план безопасности. Ниже названия пересказаны по смыслу; примеры — учебная привязка к Frontend.

| Категория 2025 | Пример обсуждения |
|---|---|
| A01 Нарушения контроля доступа | Доступ к чужому заказу по id |
| A02 Ошибочная конфигурация безопасности | Отладочный endpoint открыт в production |
| A03 Сбои безопасности цепочки поставки | Скомпрометированная зависимость или CI |
| A04 Криптографические проблемы | Передача чувствительных данных без нужной защиты |
| A05 Инъекции | Недоверенный HTML попал в исполняемый контекст |
| A06 Небезопасное проектирование | Процесс допускает обход обязательного этапа проверки |
| A07 Ошибки аутентификации | Неверный жизненный цикл сессии |
| A08 Нарушения целостности ПО или данных | Доверие неподтверждённому обновлению |
| A09 Недостатки логирования и оповещений безопасности | Аномальные попытки входа не замечены |
| A10 Неправильная обработка исключительных ситуаций | Ошибка приводит к разрешению запрещённой операции |

**Практика:** выбери три риска для приложения заказов: актив → граница доверия → сценарий → защита → проверка. Не нужно заучивать только номера категорий.

## SEC-07. Как построить модель угроз для загрузки документа?

**Короткий ответ.** Описываю защищаемые данные, участников, поток данных и границы доверия. Для каждой границы рассматриваю злоупотребления, оцениваю ущерб, назначаю меры и способ их проверки. Модель пересматривают при изменении архитектуры.

**Пример по шагам.** Браузер просит ссылку на загрузку → API проверяет права → хранилище принимает файл → обработчик извлекает содержимое. Угрозы: чужой orderId, чрезмерный размер, вредоносное содержимое, публичный доступ. Проверка браузера полезна для UX, сервер обязан независимо проверять ограничения.

**Практика.** Пользователь меняет orderId перед запросом подписанной ссылки. Где должна сработать защита?

<details>
<summary>Разбор практики</summary>

API проверяет доступ пользователя к конкретному заказу до выдачи ссылки. Ссылка имеет ограниченные полномочия и срок. После загрузки проверяется содержимое. Успех теста — отсутствие доступа к чужому объекту даже при изменённом запросе, а не скрытая кнопка.

</details>

**Уточнение.** Как изменится модель при добавлении внешнего сервиса OCR? Появится получатель документов и новая граница доверия.

<a id="sec-08"></a>

## SEC-08. Что Frontend-разработчик должен учитывать при работе с персональными данными?

**Короткий ответ.** Сначала выясняю цель, применимое право, основание обработки и получателей данных. Затем минимизирую сбор, ограничиваю доступ, исключаю лишние данные из URL, логов и аналитики. Согласие — не единственное возможное основание по GDPR. Конкретные требования согласуем с ответственным за защиту данных.

**Пример по шагам.** Форма просит паспорт для обычной подписки. Проверяем необходимость поля. Убираем необязательный сбор; отдельно проверяем, что аналитика и запись сессии не отправляют содержимое формы. Для применимого GDPR учитываем минимизацию, сроки хранения и защиту по проекту (статьи 5, 25, 32). Для РК проверяем действующий закон о персональных данных, условия хранения и передачи для конкретной системы.

**Практика.** SDK аналитики получает email из URL и содержимое поля паспорта. Составь план исправления.

<details>
<summary>Разбор практики</summary>

Прекратить лишнюю передачу, убрать данные из URL, настроить исключения и маскирование, проверить реальные исходящие запросы. Выяснить уже переданные данные и получателей, согласовать последующие действия с ответственным за данные. Маскирование на экране не доказывает отсутствие передачи.

</details>

**Уточнение.** Достаточна ли галочка согласия, чтобы отправить любые данные любому SDK? Нет: цель, основание, объём и получатели требуют отдельной проверки.

<a id="sec-09"></a>

## SEC-09. Как организовать пентест и проверить исправление находки?

**Короткий ответ.** Пентест проверяет возможность эксплуатации в согласованных границах. До начала определяют разрешённые системы, учётные записи, ограничения и контакты. Находка должна содержать воспроизведение, воздействие, доказательства и условия; после исправления нужен повторный тест.

**Пример по шагам.** Тестировщик видит чужой заказ при замене ID. Команда воспроизводит на тестовых аккаунтах, исправляет проверку принадлежности на API и проверяет чтение, изменение и вложения. Затем проводит повторный тест и добавляет регрессионную проверку.

**Практика.** После находки разработчик спрятал кнопку просмотра чужого заказа. Как принять исправление?

<details>
<summary>Разбор практики</summary>

Нельзя принять по UI: проверяем прямой HTTP-запрос с чужим ID и разные роли. Сервер должен отклонить доступ. Фиксируем отрицательные и разрешённые сценарии. Проверка проводится только в согласованной области.

</details>

**Уточнение.** Чем сканер отличается от полноценного пентеста? Автоматизация не гарантирует обнаружения ошибок бизнес-логики и цепочек эксплуатации.
