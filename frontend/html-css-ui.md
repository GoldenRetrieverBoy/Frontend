## UI-01. Зачем семантика, если div можно стилизовать как угодно?

**Ответ.** HTML сообщает смысл и даёт встроенное поведение. button уже имеет клавиатурное взаимодействие и роль кнопки; ссылка с href — навигацию и возможность открыть адрес отдельно. Семантика помогает средствам доступности и пониманию структуры страницы поисковыми системами, но сама по себе не гарантирует позицию в поиске.

```html
<nav aria-label="Основная навигация"><a href="/orders">Заказы</a></nav>
<main>
  <h1>Заказы</h1>
  <button type="button">Обновить</button>
</main>
```

В форме button без type может отправить форму. `div role="button"` не приобретает клавиатурное поведение автоматически. Заголовки выбираем по структуре, внешний вид задаём CSS.

**Практика:** замени кликабельные div в карточке на подходящие элементы, не вложив кнопку в ссылку. **Уточнение:** когда действие должно быть ссылкой? Когда его смысл — перейти к ресурсу.

**Критерий самопроверки:** Переход и действие доступны клавиатурой и не вложены друг в друга.

<details>
<summary>Разбор практики — открой после самостоятельной попытки</summary>

Название товара оформляем ссылкой с href, добавление в корзину — соседней button type="button". Кнопку не вкладываем в ссылку и не заменяем ссылку обработчиком div. Проверяем Tab, Enter для ссылки, Enter/Space для кнопки и доступные имена. Нажатие кнопки не должно переходить на страницу товара.

</details>

## UI-02. Как сделать доступную форму и диалог?

**Ответ.** Полю нужны доступное имя, понятная ошибка и связь ошибки с полем. Интерфейс должен работать с клавиатуры, иметь видимый фокус и не полагаться только на цвет. Диалог требует имени, корректного начального фокуса, поведения Escape, ограничения взаимодействия с фоном и возврата фокуса после закрытия.

```html
<label for="email">Почта</label>
<input id="email" type="email" autocomplete="email"
       aria-invalid="true" aria-describedby="email-error">
<p id="email-error">Укажите адрес в формате name@example.com</p>
```

aria-invalid выставляем при реальной ошибке, а не навсегда. Placeholder не заменяет label. Нативный dialog с showModal даёт часть модального поведения, но имя, сценарий фокуса и проверку в целевых браузерах всё равно проектируем. Для собственного диалога реализуем фокус и фон явно.

**Практика:** пройти форму Tab/Shift+Tab/Enter/Escape, проверить чтение ошибки и возврат фокуса. **Ошибка:** положительный tabindex для «исправления» порядка, расходящегося с DOM.

**Критерий самопроверки:** Пройден полный сценарий без мыши: открытие, ошибка, исправление, закрытие и возврат фокуса.

<details>
<summary>Разбор практики — открой после самостоятельной попытки</summary>

При открытии модального диалога переводим фокус внутрь, Tab/Shift+Tab не уводят его в фон. Поля имеют label, ошибка связана с полем и доступна вспомогательной технологии. Enter отправляет форму по её контракту; Escape закрывает разрешённый к закрытию диалог. После закрытия фокус возвращается на вызвавший элемент, если он существует. Проверяем порядок DOM без положительного tabindex и повторное открытие.

</details>

## UI-03. Как браузер выбирает CSS-правило?

**Ответ.** Каскад учитывает применимость правила, происхождение, важность и слои, затем специфичность и другие правила разрешения равенства, включая порядок. Поэтому правило «id всегда сильнее class» неполное. Специфичность сравнивается внутри соответствующего уровня каскада.

```css
.button { color: blue; }
.toolbar .button { color: green; }
/* При одинаковом происхождении/важности/слое второе специфичнее. */
:where(.toolbar) .button { border: 1px solid; }
```

:where не добавляет специфичность своих аргументов. Наследование и каскад не одно и то же: не все свойства наследуются. !important усложняет переопределение и не исправляет архитектуру стилей. Scoped CSS Vue преобразует селекторы, а не создаёт Shadow DOM.

**Практика:** в DevTools найти выигравшее объявление и объяснить, почему остальные зачёркнуты. **Уточнение:** что изменится при cascade layers? Порядок слоёв участвует до специфичности; для important порядок слоёв обращается.

**Критерий самопроверки:** Для одного свойства показано выигравшее объявление и причина проигрыша конкурентов.

<details>
<summary>Разбор практики — открой после самостоятельной попытки</summary>

Для .card { color: red } и .card.active { color: blue } в одном origin/layer без important у активной карточки выигрывает более специфичное второе правило. В DevTools фиксируем файл и селектор. Если добавить important в первое, одной специфичности второго уже недостаточно. Для разных cascade layers сначала учитываем приоритет слоя; у important порядок слоёв обратный. Не сводим весь каскад к правилу «последняя строка побеждает».

</details>

## UI-04. Почему flex-элемент не сжимается и когда нужен Grid?

**Ответ.** Flex удобно распределяет элементы вдоль основной оси, Grid задаёт строки и столбцы. Intrinsic sizing и минимальные размеры содержимого могут мешать ожидаемому сжатию. box-sizing определяет, входят ли padding и border в заданный размер.

```css
* { box-sizing: border-box; }
.row { display: flex; gap: 12px; }
.title { min-width: 0; overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }
.grid { display: grid; grid-template-columns: repeat(2, minmax(0, 1fr)); gap: 16px; }
@media (max-width: 40rem) { .grid { grid-template-columns: 1fr; } }
```

`min-width: 0` разрешает flex/grid item стать меньше автоматического минимального размера. Media query отвечает условиям среды; контейнерные запросы могут быть дополнением, когда компонент зависит от размера контейнера.

**Практика:** карточка с очень длинным словом, узкий экран, увеличение шрифта. Не скрывай весь overflow страницы, чтобы замаскировать причину.

**Критерий самопроверки:** Длинное слово не ломает ширину карточки на узком экране и при увеличении текста.

<details>
<summary>Разбор практики — открой после самостоятельной попытки</summary>

У сжимаемого flex-потомка проверяем min-width: auto; при необходимости задаём min-width: 0 и политику переноса текста, например overflow-wrap: anywhere. Для сетки проверяем минимальную ширину трека, при необходимости minmax(0, 1fr). Повторяем с обычным текстом, длинным токеном и увеличенным шрифтом. Скрытие горизонтального overflow всей страницы может обрезать контент и не объясняет причину.

</details>

## UI-05. Почему z-index:999999 не помогает?

**Ответ.** Элементы сравниваются в пределах stacking context. Потомок не может своим z-index выйти выше чужого контекста, который расположен выше контекста его родителя. Контексты могут создавать transform, opacity и другие свойства.

**Пример.** Диалог находится внутри блока с transform, а соседняя шапка — в контексте выше. Увеличение z-index диалога внутри старого контекста не решает задачу. Проверяем дерево контекстов, при необходимости переносим overlay, например через Teleport; нативный модальный dialog использует top layer.

**Практика:** объясни разницу clipping из-за overflow и перекрытия из-за stacking context: перенос решает не все проблемы автоматически. **Ошибка:** бесконечно увеличивать числа без анализа родителей.

**Критерий самопроверки:** Перекрытие и обрезка воспроизведены отдельно; исправление не зависит от произвольно большого z-index.

<details>
<summary>Разбор практики — открой после самостоятельной попытки</summary>

При stacking context смотрим контексты предков: дочерний z-index сравнивается внутри своего контекста и не поднимает весь родительский контекст. При overflow часть элемента обрезается границей контейнера независимо от большого z-index. Проверяем отключение конкретного свойства и подходящее размещение overlay вне обрезающего контейнера. После переноса повторно проверяем позиционирование, прокрутку и фокус.

</details>

## UI-06. BEM, utility first и состояния — как выбрать?

**Ответ.** BEM именует сущности и их варианты; utility first собирает стиль из небольших утилит. Выбор зависит от команды, дизайн-системы и повторяемости. В обоих подходах нужны токены, ограниченные варианты и понятное владение стилями.

```css
.button:hover { background: #ddd; }
.button:active { transform: translateY(1px); }
.button:focus-visible { outline: 2px solid #174ea6; outline-offset: 3px; }
.button:disabled { opacity: .55; }
```

disabled реально ограничивает нативное взаимодействие; aria-disabled только объявляет состояние, поведение нужно реализовать. Hover нельзя делать единственным способом узнать важную информацию, поскольку есть touch и клавиатура.

**Практика:** опиши состояния submit при ожидании, ошибке и успехе. Реши, как предотвратить повторное действие и сохранить понятную обратную связь.

**Критерий самопроверки:** Ожидание, ошибка и успех различимы; двойная отправка блокируется, введённые данные не теряются.

<details>
<summary>Разбор практики — открой после самостоятельной попытки</summary>

При submitting блокируем повторный запуск в обработчике и показываем состояние ожидания. После ошибки сохраняем поля, выводим сообщение и разрешаем осмысленный повтор. После успеха показываем подтверждение с результатом. Проверяем двойной клик, Enter во время ожидания и сетевой сбой. Disabled-кнопка улучшает UI, но защита эффекта от дублей требует серверного контракта.

</details>
