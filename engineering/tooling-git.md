## TOOL-01. Зачем package manager и lockfile?

**Ответ.** Менеджер пакетов разрешает зависимости, скачивает их и связывает доступные пакеты. package.json задаёт намерение и диапазоны, lockfile фиксирует разрешённый граф и связанные данные для воспроизводимой установки. Воспроизводимость также зависит от версии среды, платформы и install scripts.

```sh
npm ci
npm ls
npm explain some-package
```

Это учебные команды: some-package заменяем реальным пакетом. npm ci рассчитан на установку по согласованному lockfile и удаляет существующий node_modules; это не обычное добавление пакета. dependencies нужны потребителям/исполнению по контракту пакета, devDependencies — разработке и сборке; peerDependencies задают совместимость с зависимостью окружения потребителя. В статической SPA браузер получает bundle, а не читает эти разделы.

**Практика:** локально сборка проходит, в CI нет. Сравни Node/package manager, lockfile, env, регистр путей и scripts. **Ошибка:** лечить проблему удалением lockfile без анализа изменений графа.

**Критерий самопроверки:** Сравнение локальной и CI-среды приводит к конкретной воспроизводимой разнице.

<details>
<summary>Разбор практики — открой после самостоятельной попытки</summary>

Фиксируем версии Node и package manager, проверяем одинаковый lockfile и команду установки, переменные и регистр импортируемых путей. Повторяем чистую установку из lockfile и сборку в сопоставимой среде. Если причина — импорт с неверным регистром, исправляем путь и проверяем на чувствительной к регистру файловой системе. Удаление lockfile меняет сразу много зависимостей и не объясняет исходный сбой.

</details>

## TOOL-02. Как работает bundler и чем dev отличается от build?

**Ответ.** Сборщик строит граф модулей, преобразует исходники и ресурсы, оптимизирует и формирует выходные файлы. Dev-сервер делает акцент на быстром обновлении и диагностике; production-сборка — на распространяемых артефактах. Названия внутренних движков Vite зависят от версии, поэтому на интервью отделяю архитектурную идею от версии реализации.

**Пример.** Импорт тяжёлого отчёта через dynamic import создаёт возможность отдельной загрузки. Tree shaking убирает доказуемо ненужный код при подходящей структуре модулей и учёте side effects; минификация только уменьшает представление. Source maps связывают результирующий JS с исходником.

**Практика:** найти пакет, который увеличил initial bundle, и проверить граф импортов. **Уточнение:** почему dev работает, build падает? Различаются env, преобразования, пути, оптимизации; типы могут проверяться отдельной командой.

**Критерий самопроверки:** Увеличение размера связано с конкретным импортом и проверено production-сборкой.

<details>
<summary>Разбор практики — открой после самостоятельной попытки</summary>

Сравниваем отчёты размеров до/после на одинаковой конфигурации, находим пакет и цепочку его попадания в entry. Проверяем прямой импорт, общий barrel и побочные эффекты. Удаляем ненужный импорт или переносим действительно отложенную возможность и повторяем build/Network. Размер установленного пакета не равен размеру переданного initial bundle; dev-сервер не заменяет эту проверку.

</details>

## TOOL-03. Как оптимизировать bundle и писать плагин?

**Ответ.** Сначала измеряю исходный/сжатый размер и реальную стоимость загрузки/исполнения. Затем смотрю дубли зависимостей, широкие импорты, локали, статические ресурсы и границы ленивой загрузки. Больше чанков не всегда лучше: есть накладные расходы и риск waterfall.

```js
// Учебный Vite-плагин: добавляет метку в HTML.
export default {
  plugins: [{
    name: 'build-label',
    transformIndexHtml(html) {
      return html.replace('</head>', '<meta name="build-kind" content="training"></head>');
    },
  }],
};
```

Пример предполагает Vite config с HTML-entry. Для реального плагина выбираем API нужной версии, проверяем dev/build, sourcemaps при трансформациях JS и отсутствие секретов. Для генерации константы существующий механизм config может быть проще собственного плагина.

**Практика:** общий vendor chunk вырос до нескольких мегабайт. Реши, какие зависимости нужны первой странице, а какие только отчёту, и проверь Network после разделения.

**Критерий самопроверки:** Код отчёта отсутствует в начальной загрузке и появляется при открытии отчёта без поломки функции.

<details>
<summary>Разбор практики — открой после самостоятельной попытки</summary>

Находим зависимости, нужные только отчёту, и проверяем отсутствие статического импорта из общего entry. Создаём границу динамической загрузки отчёта; общий код оставляем там, где его реально используют. В Network с очищенным кэшем сравниваем первую страницу и затем отчёт, включая число запросов и задержку его открытия. Одно переименование vendor chunk не уменьшает initial загрузку, если он всё ещё требуется entry.

</details>

## TOOL-04. Зачем линтер и monorepo?

**Ответ.** Линтер проверяет договорённости и потенциальные ошибки; type checker проверяет типовые отношения; formatter — оформление. Они решают разные задачи. Monorepo объединяет проекты в одном репозитории, но требует управлять графом пакетов, публичными API, задачами, версиями и кэшем сборок.

**Пример.** Два приложения используют UI-kit. Изменение токена должно перезапустить затронутые проверки; кэш обязан учитывать входы, lockfile и значимые env. Неверный cache key может вернуть успешный, но чужой артефакт. Turborepo/Lerna — инструменты, а не обязательная архитектура любого репозитория.

**Практика:** введи правило запрета внутреннего импорта библиотеки и план постепенного исправления старых нарушений. **Ошибка:** включить множество правил без объяснения и оставить массовые disable.

**Критерий самопроверки:** Новые внутренние импорты блокируются, разрешённый публичный API работает, старые исключения имеют план удаления.

<details>
<summary>Разбор практики — открой после самостоятельной попытки</summary>

Для импорта library/internal/* вводим целевое правило на границе библиотеки, документируем публичные exports. Разбираем существующие нарушения по потребителям и исправляем постепенно с владельцем и сроком исключений. Проверяем один запрещённый и один разрешённый импорт. Правило не должно блокировать внутреннюю работу самой библиотеки; массовый disable без области и срока уничтожает защиту.

</details>

## TOOL-05. Что хранит Git и чем reset отличается от revert?

**Ответ.** Коммит описывает снимок и родителей; ветка — перемещаемая ссылка, HEAD — текущая точка. Рабочее дерево, index и история — разные состояния. reset передвигает ссылку и в зависимости от режима меняет index/рабочее дерево. revert добавляет обратное изменение новым коммитом и обычно удобнее для опубликованной общей истории.

```sh
git status --short
git diff
git diff --staged
git log --oneline --graph -10
git diff main...feature
```

Последняя команда показывает изменения feature относительно общего предка при существующих refs. clone создаёт локальную копию, add готовит index, commit фиксирует, fetch обновляет удалённые refs, pull дополнительно интегрирует, push публикует. SSH обеспечивает транспортную аутентификацию; приватный ключ не передают в репозиторий.

**Практика:** случайно добавлен debug-код, остальное нужно сохранить. Назови состояние изменения и точечный способ убрать его. Не предлагай reset --hard без оценки потери данных.

**Критерий самопроверки:** Удалён только debug-фрагмент; соседнее полезное изменение остаётся в ожидаемом состоянии.

<details>
<summary>Разбор практики — открой после самостоятельной попытки</summary>

Сначала смотрим status и diff, различаем рабочее дерево, index и commit. Незакоммиченный debug удаляем точечным редактированием; если он staged, корректируем index выборочно и проверяем оба diff. В опубликованном commit создаём новое исправление, не переписывая общую историю. Revert всего commit подходит только если нужно отменить весь его смысл; для смешанного commit он уберёт и полезную часть.

</details>

## TOOL-06. Merge, rebase и cherry-pick — как выбрать?

**Ответ.** Merge объединяет линии истории, rebase воспроизводит изменения на другой базе и создаёт новые коммиты, cherry-pick переносит выбранное изменение. При конфликте нужно восстановить смысл обоих изменений, а не автоматически выбрать ours/theirs.

**Пример.** Hotfix нужен в release и develop: выбираем перенос с учётом процесса, затем проверяем, что логика не дублируется при следующем merge. Rebase опубликованной ветки требует координации, поскольку меняет идентификаторы. Reflog может помочь найти потерянную локальную точку, но не заменяет резервирование.

**Практика:** два разработчика изменили один API-контракт. Опиши чтение обеих версий, согласование итогового типа, тесты потребителей и завершение конфликта.

**Критерий самопроверки:** Итоговый контракт согласован, маркеров конфликта нет, оба потребителя проверены.

<details>
<summary>Разбор практики — открой после самостоятельной попытки</summary>

Читаем базовую версию и намерение обеих правок, выбираем совместимый итоговый тип или явную миграцию. Вручную объединяем смысл, обновляем вызовы и запускаем проверки обоих потребителей. Затем просматриваем итоговый diff и продолжаем выбранную Git-операцию. Автоматический выбор ours/theirs для всего файла может удалить нужную часть другой реализации.

</details>

## TOOL-07. GitFlow, Trunk Based и GitLab — что проверят у Middle 3?

**Ответ.** GitFlow использует отдельные долгоживущие ветки и релизные потоки; Trunk Based опирается на частую интеграцию небольших изменений и обычно короткие ветки. Выбор зависит от релизов и проверки, а не от моды. Feature flags отделяют интеграцию кода от доступности функции, но требуют удаления устаревших флагов.

GitLab MR — площадка проверки изменения; управление репозиторием включает защищённые ветки, права, owners и правила интеграции. Webhook отправляет события внешней системе; получатель проверяет подлинность по возможностям интеграции и обрабатывает дубли/повторы. Успешный HTTP webhook ещё не означает бизнес-успех обработки.

**Практика:** предложи правила MR для общей библиотеки: потребители, совместимость, проверки, выпуск версии, миграция. **Ошибка:** выдавать широкие права ради обхода падающей проверки.

**Критерий самопроверки:** MR библиотеки проверяет совместимость потребителей и описывает выпуск, миграцию и владельца.

<details>
<summary>Разбор практики — открой после самостоятельной попытки</summary>

В описании указываем изменённый публичный контракт и затронутых потребителей. Запускаем проверки самой библиотеки и репрезентативных интеграций; breaking change сопровождаем согласованной версией и инструкцией миграции. Требуем актуальные проверки итогового состояния и review владельца по правилам команды. После выпуска проверяем переход потребителей; обход failed pipeline широкими правами не доказывает совместимость.

</details>

## TOOL-08. Как провести Merge Request от ветки до безопасного слияния?

**Короткий ответ.** Делаю небольшое изменение с понятной целью, проверками и описанием результата. Учитываю базовую ветку, конфликты, обязательные проверки и замечания. Перед слиянием проверяю итоговый diff, а не только свой последний коммит.

**Пример по шагам.** В MR исправляется расчёт скидки. В описании есть пример до/после и результат теста. Reviewer просит проверить нулевую сумму. После изменения запускается новая проверка именно последней версии; старый зелёный pipeline не подтверждает новый код.

**Практика.** В ветке появились изменения другого разработчика после review. Что проверить до merge?

<details>
<summary>Разбор практики</summary>

Просмотреть новый diff и конфликтные места, запустить проверки итогового состояния, получить необходимое повторное review. Не обходить правила protected branch. Размер MR и ясная цель уменьшают риск пропуска ошибки.

</details>

## TOOL-09. Как обрабатывать повторную доставку webhook?

**Короткий ответ.** Получатель проверяет источник по согласованному механизму, валидирует событие и учитывает повторную доставку. Эффект защищается идентификатором события или другим ключом идемпотентности. Подтверждение доставки и выполнение долгой работы обычно разделяют.

**Пример по шагам.** Событие о merge создаёт задачу в трекере. Отправитель не получил ответ и повторил событие. Получатель видит уже обработанный eventId и не создаёт вторую задачу. Запись статуса должна выдерживать конкурентные запросы и сбои.

**Практика.** Два одинаковых события пришли одновременно. Достаточно ли сначала проверить наличие ID, а потом записать его?

<details>
<summary>Разбор практики</summary>

Нет: оба обработчика могут пройти проверку. Нужна атомарная уникальность/захват и согласование статуса с эффектом. Если трекер поддерживает идемпотентный ключ, используем его; иначе отдельно разбираем окно сбоя между созданием задачи и записью результата.

</details>

## TOOL-10. Как защитить репозиторий, секреты и pipeline?

**Короткий ответ.** Ограничиваю права по роли и необходимости; задаю правила для защищённых веток и релизов. Секреты доступны только доверенным jobs и окружениям. Код pipeline из внешнего MR рассматриваю как исполняемый код с возможностью читать доступные ему credentials.

**Пример по шагам.** Внешний MR меняет CI-скрипт и печатает переменные. Маскирование логов не гарантирует защиту: скрипт может преобразовать значение или отправить его наружу. Поэтому production-секреты вообще не должны попадать в такое выполнение.

**Практика.** Команде нужен preview внешнего MR. Как отделить его от production-доступов?

<details>
<summary>Разбор практики</summary>

Изолировать preview-окружение и права, не передавать production-секреты, ограничить runner и сетевые полномочия, задать правила публикации и удаления preview. После утечки требуется отзыв/ротация, а не только удаление строки из git.

</details>
